# Agent memory for Taut — research (Sept 2026)

## 1. Framing

Taut agents are headless CLI processes (Claude Code first) that run per task with a fresh context. "Memory" here means: everything an agent was ever told (channel messages it could see, DMs, threads, task results, files) plus its own notes, recallable mid-task through a tool. Constraints: one Docker container, SQLite, €4 VPS (~2 vCPU / 4 GB), OSS only, hard per-agent isolation. The 2026 industry pattern is a two-tier system: a small always-loaded markdown index (CLAUDE.md / MEMORY.md style) plus on-demand search over an indexed store. The honest evidence says the _search tool_ matters more than the _store_: hybrid BM25+dense with RRF over message-level rows beats both pure-vector and pure-graph at this scale, and plain grep-style search over files is already competitive. Graph memory buys ~2 points on benchmarks at large LLM cost and is not worth it for Taut.

## 5. What the evidence says

- **File-based + grep is not a strawman.** Claude Code, Codex and Karpathy's wiki all ship markdown + an always-loaded index and _no_ semantic index; Letta's filesystem agent beat Mem0 on LoCoMo; Anthropic argues just-in-time grep avoids stale indexes. For _curated_ knowledge (preferences, decisions, procedures) this tier is sufficient and should be the agent's notes layer.
- **But raw chat history is different.** "What did Ana say about the invoice format in June?" is a paraphrase over months of noise; BM25 needs the right term, dense needs the right meaning. Hybrid with RRF is the cheapest robust answer (LanceDB, Graphiti, Hindsight, memsearch, Mem0 all converged on it), and Anthropic measured BM25+embeddings at −49% failures vs embeddings alone. LongMemEval shows the two design choices that matter for chat: index at _message/round_ granularity, and make time a first-class filter ("3 months ago" is a `WHERE`, not a vector).
- **LLM-extracted "facts" (Mem0-style) lose verbatim recall.** A Slack agent must quote exactly what was said; store the raw message and let the LLM summarize at read time.
- **Graph memory is not worth it here.** +~2% in Mem0's own paper, Graphiti/LightRAG/GraphRAG need an LLM call per message on ingest, and a second database. Temporal validity ("X was true until Y") is handled by `message.updated` + timestamps.
- **Reranking is the biggest cheap win after hybrid** (−67% total with rerank per Anthropic); a 22M cross-encoder runs on CPU; Voyage rerank-2.5-lite is $0.02/M as the key-upgrade.
- **Store choice matters less than the tool contract**; SQLite FTS5 + sqlite-vec fits a 4 GB box up to a few hundred thousand chunks per agent, which is years of chat for a small company.

## 6. Recommended design for Taut

**Storage layout (one SQLite file per agent — isolation by construction, `rm -rf` to forget):**

```
/data/companies/<slug>/agents/<handle>/memory/
├── memory.db        # SQLite: messages, chunks, FTS5 (external content), vec0, meta(last_seq)
├── MEMORY.md        # agent-curated index, ≤200 lines / 25 KB, rendered into CLAUDE.md at spawn
├── notes/           # agent-authored markdown (one topic per file, YAML frontmatter, modified ts)
└── files/           # copies of attachments it was handed (indexed as chunks, text-extracted)
```

Tables: `items(id, kind[message|thread_summary|task_result|file|note], channel_id, thread_id, author_id, author_kind, at, text, meta_json, deleted_at)`; `items_fts` = FTS5 external-content on `text` with porter+unicode61 (triggers per FTS5 docs); `items_vec` = `vec0(item_id, embedding float[384] distance_metric=cosine, channel_id text partition key, at_day integer, kind text, +preview text)`; `meta(key, value)` holds `last_seq`, `embedding_model`, `dims`.

**Ingestion (event-log consumer per agent, incremental):**

- Subscribe to the company bus from `meta.last_seq`; for each `message.created` deliver to every agent that _can see it_: channel members (agents included), DM recipient, thread participants. Also ingest `agent.task.done` summaries (kind=task_result) and inbox files (kind=file, text-extracted). Idempotent on `message_id`; commit `last_seq` in the same transaction. If `last_seq` is older than the 7-day retained log, rescan the `messages` table by `seq`.
- Unit = **one message = one row** (LongMemEval round-level). Long messages/files chunk at ~400 tokens with 50 overlap. Contextual prefix without an LLM: `"[#channel] [author] [YYYY-MM-DD] [thread: <first 80 chars of root>] "` embedded and FTS-indexed alongside the text (cheap contextual retrieval; LLM-written context later, with prompt caching).
- `message.updated` → delete+insert FTS row and vec row (vec0 `INSERT OR REPLACE` only in alpha; use DELETE+INSERT on v0.1.9). `message.deleted` → hard delete from every recipient agent's DB (not soft) so a retracted message cannot be recalled. Notes are never touched by ingestion.
- Embedding runs in a small in-process queue (≤ concurrency 1 on 2 vCPU); embed once per message, write the same vector into each recipient's DB.
- Nightly "sleep-time" job (optional, uses the company's subscription): summarize each thread the agent participated in into a `thread_summary` row, and let the agent rewrite `MEMORY.md` (Codex/Letta consolidation pattern).

**Embeddings:** default local `bge-small-en-v1.5` (q8 ONNX via Transformers.js, ~35 MB, 384d, 512 tokens; MIT) — fast enough for 2 vCPU ingest and query. Config switch to `nomic-embed-text-v1.5@256d` (Apache-2.0, 8k ctx, better for long messages/other languages) or `EmbeddingGemma-300m` (best <500M, Gemma licence). Company-key upgrade: if a `voyage.api_key` vault item exists, embed with `voyage-4-lite` ($0.02/M) at 512d and rerank with `rerank-2.5-lite`; the ideal path is local `voyage-4-nano` (Apache-2.0, same vector space) so the upgrade needs no re-index — adopt once an ONNX build is verified. Model + dims are recorded in `meta`; changing them triggers a background re-embed. Never use OpenAI embeddings by default (OpenAI key ≠ Anthropic key in Taut's vault model).

**Retrieval pipeline (`memory.search`):** parse filters (channel, author, since/until, kind) → FTS5 `bm25()` top-50 with the same WHERE → vec0 KNN top-50 with partition/metadata WHERE (`at_day` range, kind) → RRF (k=60) → optional cross-encoder rerank of top-30 (ms-marco-MiniLM local; Voyage if key) → mild recency tiebreak (Generative-Agents style 0.995^days, weight 0.1) → return top-10 with `{item_id, channel, author, at, text, thread_id, permalink}`. Target <150 ms on 100k rows.

**MCP tool surface (stdio server spawned in the sandbox; also a `taut-mem` CLI that hits the same socket, because CLIs are "in the training data"):**

- `memory.search(query, {channel?, author?, since?, until?, kind?, limit=10})` — hybrid; returns snippets + ids.
- `memory.grep(pattern, {since?, channel?})` — raw FTS/`LIKE`/trigram for exact strings (ticket ids, URLs).
- `memory.recall_thread(thread_id | message_id, {before=20, after=20})` — verbatim, chronological.
- `memory.timeline(since, until, {channel?})` — paged chronological browse ("what happened last week").
- `memory.note(title, body, {tags})` / `memory.notes.list()` / `memory.notes.get(id)` / `memory.forget(note_id)` — writes `notes/<slug>.md`, indexes it as kind=note; only notes are deletable by the agent.
- `memory.index_hint()` — returns `MEMORY.md` (also rendered into CLAUDE.md via `@memory/MEMORY.md` at spawn, so the always-loaded tier mirrors Claude Code).

**Isolation guarantees:** (1) memory lives in the Taut API process; the runtime user `taut-agent` cannot read `/data`; (2) at spawn Taut mints a per-task token bound to `(company_id, agent_id, task_id)` and exports `TAUT_MEMORY_TOKEN` + a unix socket path; the MCP shim forwards calls with the token and never receives a path; (3) the server resolves token → single DB file, so cross-agent search is impossible by construction (no `WHERE agent_id` to forget); (4) notes paths are validated to stay under `notes/` (memory-tool traversal guidance); (5) audit each call to `.taut/audit.log`; (6) deleting an agent deletes its folder.

**MVP cut (one weekend):** per-agent `memory.db` with FTS5 only (no embeddings); event-log consumer with `last_seq`, visibility fan-out, edit/delete handling; `memory.search` (BM25 + filters), `memory.recall_thread`, `memory.timeline`, `memory.note`; `MEMORY.md` import into CLAUDE.md; MCP stdio shim + `taut-mem` CLI; token-scoped socket. This alone reproduces the Letta "files + grep" result.

**Next:** sqlite-vec + bge-small dense + RRF; local cross-encoder rerank; Voyage key upgrade; nightly thread summaries + `MEMORY.md` consolidation; file text extraction; LanceDB tier for agents past ~1M chunks (or sqlite-vec DiskANN once out of alpha); per-agent memory UI in the web client (browse/delete notes, audit).
