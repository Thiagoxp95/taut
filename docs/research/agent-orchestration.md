# Agent orchestration: chat as the bus?

Research date: 2026-09-08. Primary sources only (repos, READMEs, source, docs sites, issue trackers). Sandboxes/machines are covered separately in `agent-sandboxes.md`.

## 1. Use case

A Taut company is split into departments. Each department has **one human coordinator** who directs that department's agents through chat. Agents run as Claude Code / Codex / Cursor CLI / OpenCode processes, each on its own machine, spawned per task (`agent-model.md` §5, §7). Agents must eventually message each other: ask a question, hand off a task, report done. The question is whether any external orchestration tool adds enough to justify a dependency, or whether Taut's own channels, threads, @mentions and per-company seq-numbered event log (`agent-model.md` §6) should _be_ the bus, exposed to agents as an MCP server / CLI (`taut send @handle …`, `taut inbox`).

## 3. Per-tool notes

**Orca ADE** — https://github.com/stablyai/orca. Electron "ADE for a fleet of parallel agents"; orchestration is an _Experimental_ CLI layer. Model: Run → Task (`pending|ready|dispatched|completed|failed|blocked`) → Dispatch → Message; subcommands `run-create run-use send check reply inbox task-create task-list task-update dispatch dispatch-show ask gate-create gate-resolve gate-list reset` plus `worker-start|show|read|stop|abandon|release|retain|list` (`src/cli/specs/orchestration*.ts`) [2]. `worker-start` takes `--deps <json_array>`, `--parent`, `--agent`, `--on <saved-environment>` [2]. `check --wait --types … --timeout-ms` blocks; a returned Delivery is a whole FIFO batch replayed until `--ack` [2]. `ask` "durably records a question… and blocks until the coordinator replies"; `--resume <message_id>` after timeout [3]. The injected worker preamble hard-codes: send `worker_done` exactly once with `--task-id` and `--dispatch-id` (so a stale retry can't complete the current attempt), heartbeat every 5 min, "NEVER use AskUserQuestion", check inbox at checkpoints, and after `worker_done` "stop… do NOT run a sleep/poll loop" [3]. Store is `better-sqlite3`-style SQLite in WAL [4]. Decision gates: "the coordinator never auto-resolves gates (humans do…) — that would defeat them as approval checkpoints" [7]. Cross-host: `orcad`/`orca serve` binds `ws://` (loopback default, SSH port-forward) and a federation sync pulls `to_home` relay pages of 50 [5]. **Reliability of the PTY path is the dominant issue cluster**: #10416 long injections silently truncated yet "dispatched"; #10728 submit lost while TUI boots; #10666 injection answers Codex's trust prompt and swallows the task; #9976 tui-idle false positive loses dispatch; #17066/#16660 `agent_prompt_stalled` revokes capability so `worker_done` is rejected; #13678 injected lane invisible to `worker-*`; #11499 completed task reverts to ready; #14898 `dispatchShow` leaks another Run's context; #16075 Claude Code overrides `/orchestration` with native subagents [6]. Bus factor ≈4 core humans [1].

**Bernstein** — https://github.com/sipyourdrink-ltd/bernstein (PyPI `bernstein`). "Deterministic scheduler — no model in the coordination loop"; one LLM "Manager" call plans, Python ticks claim tasks, spawn one-shot CLI agents in worktrees, a "Janitor" verifies signals, FIFO merge queue [8][9]. Agents talk back via signal files, REST (`POST /tasks/{id}/complete` with a `worker-completion/v1` contract), MCP; agent↔agent is a pull-based bulletin board and a per-task mailbox with closed `kind ∈ {finding, artefact_ref, question}`, 4 KB cap, `since_seq` cursor, rendered into the next spawn's prompt — no interrupt of a running agent [9]. Cluster mode: central server + worker nodes that "never talk to each other" [9]. Huge surface for one maintainer; issues show the classic worktree/heartbeat/merge-back failures (#2810, #4330, #5271) [9].

**Vibe Kanban** — https://github.com/BloopAI/vibe-kanban. Rust local server + web kanban; each workspace "a branch, a terminal, and a dev server"; humans orchestrate [10]. `crates/mcp/src/bin/vibe_kanban_mcp.rs` is a stdio MCP that calls the local HTTP API; `McpMode::Orchestrator` pre-binds a session context and offers `create_workspace` (executor enum includes `CLAUDE_CODE, CODEX, OPENCODE, CURSOR_AGENT`) and "Run a coding agent turn in an existing session and return immediately" — request/response, not chat; undocumented in `docs/` [12][46]. It also writes its MCP entry into each agent's own config file (`crates/executors/src/mcp_config.rs`) [46]. Shut down 2026-04-10 ("couldn't find a business model"), community-maintained; last push 2026-04-24 [11][10].

**Claude Squad** — https://github.com/smtg-ai/claude-squad. Go TUI; `exec.Command("tmux","new-session",…)` per agent, prompt delivered by `SendKeys` + 100 ms sleep + `TapEnter` (`session/instance.go`), status by hashing pane text; the only daemon is an "AutoYes" poller that taps Enter on prompts (`daemon/daemon.go`); no inter-instance messaging, no network listener; open #266 "SendPrompt sends text before CLI is ready, prompt lost" [13][14][47]. AGPL-3.0.

**Conductor** — https://conductor.build. "Run parallel Claude Code, Codex, and Cursor agents in isolated workspaces on your Mac" (docs add OpenCode); closed source (Pro $50/mo, Teams $60/user) [15]. Conductor Cloud runs "Vercel sandboxes"; its REST API (`POST /v0/sessions`, `POST /v0/sessions/{id}/messages`, `GET …/status`, `POST /v0/sql` read-only over transcripts) and a Pro-only MCP let an agent create another workspace and prompt it; `CONDUCTOR_SESSION_ID`/`CONDUCTOR_API_TOKEN` are injected into cloud workspaces [15][48]. No coordinator persona.

**Emdash** — https://github.com/generalaction/emdash. Apache-2.0 Electron app, worktree per task, 36 agent plugins (`packages/plugins/src/agents/impl/`) incl. claude/codex/cursor/opencode, many via ACP; remote hosts run a per-user `workspace-server` daemon reachable only through an SSH-forwarded Unix socket ("The daemon exposes no TCP port"); typed `@emdash/wire` event streams with cursors and gap callbacks; local SQLite; no agent↔agent messaging (orchestrator issues #534/#322 closed) [16][49].

**Composio Agent Orchestrator** — https://github.com/ComposioHQ/agent-orchestrator → redirects to https://github.com/Untrivial-ai/agent-orchestrator. Apache-2.0 Go daemon + Electron app + `ao` CLI; "a long-running Go daemon that supervises multiple parallel AI coding agent sessions", loopback HTTP, SSE `/api/v1/events` with `Last-Event-ID` replay, SQLite with trigger-based CDC → `change_log` → SSE; "Display status is never stored. It is computed at read time from durable facts" [18]. The **project orchestrator is an ordinary Claude Code/Codex session** taught the `ao` CLI by `skillassets/using-ao/SKILL.md` (`ao spawn`, `ao send --session <id> --message`, `ao review`); REST `POST /api/v1/orchestrators/delegate` [18]. Worker→orchestrator is not event-driven: open #4951 "Lifecycle events never start an orchestrator turn — orchestrator sessions stall until a human types"; #3921 crashes at 40+ workers; #4700 restart leaves a project without an orchestrator [50]. No MCP exposed; ADR 0001/0004 add LAN + `cloudflared` listeners for the mobile app only [50].

**AgentsRoom** — https://agentsroom.dev/features/agent-messaging. Closed desktop app (macOS/Windows/Linux; Free 3 projects/6 agents, Pro €7.99/mo); messaging shipped 2026-08-23, changelog 2026-08-31 "Fixed infinite agent message loop" [19][20][51]. Now **seven** tools: `agents_list_live`, `agents_send`, `agents_message_status`, `agents_read_inbox` (peek mode), `agents_reply`, `agents_ack` (accept/decline/done), `agents_report_status` [21]. Semantics worth copying verbatim: "The message is written to disk before anyone tries to deliver it"; envelope "never rewritten… everything that happens to it later is recorded as a separate event"; delivery held if recipient is thinking or waiting on the human ("writing into that prompt would answer in your place"); "What lands is a notice, not the body" and the inbox read is what marks it read; "Read, accepted and replied are three different facts"; "The sender is never an argument. The server stamps it"; broadcast copies carry a header naming other recipients "telling the agent not to relay it"; `agents_send` "rate limited on purpose so a chain of agents relaying each other cannot turn into a message loop" [21]. Explicitly no blocking tool: "a call that waits depends on a timeout the app does not control and every provider sets differently" [21].

**agmsg** — https://github.com/fujibee/agmsg. `join.sh/send.sh/inbox.sh/history.sh/delivery.sh/spawn.sh/remote.sh`, installed as an Agent Skill (`npx agmsg`, `/agmsg` or `$agmsg`); SQLite WAL at `~/.agents/skills/agmsg/db/messages.db` with an append-only `events` table and per-(team, agent) `read_cursors` — "Mutable status — most importantly the read flag — is derived by projection over the event stream" (`ARCHITECTURE.md`); delivery via SessionStart/Stop hooks or a Monitor-fed `watch.sh`; "the file is the shared floor" — same host, optional self-hosted sync server with no authentication; no ack/reply/threads; loop control "at the protocol/prompt level" [22][23][52]. The "~500 lines" claim is stale (`delivery.sh` alone is 821 lines) [52].

**postal-mcp** — https://github.com/tkellogg/postal-mcp. README says `send_message`/`check_mailbox`; code (`postal/server.py`) is `send_to_agent(name, msg, msg_id?)` and `check_mail()`, a `while True` pop-or-`sleep(1)` with no timeout; caller identity is the URL path segment (`/agents/{name}/mcp/`), DB at `db/messages.sqlite` relative to CWD; sample prompt: "keep completing tasks forever and never ask the user for anything"; 6 commits over two days in 2025-06 [24][25][53]. agent-inbox's ADR 0011 cites it as evidence against blocking tools [54].

**agent-inbox** — https://github.com/salimfadhley/agent-inbox. "One HTTP API is the hub's only machine interface. The MCP server, the CLI and the web console are all ordinary clients"; identities issued by the hub (`join`), found by `purpose`; ActivityStreams `attributedTo/to/cc/inReplyTo`; 16 MCP tools with **tiered reads** — `unread_count` → `check_threads` → `check_inbox` ("a manifest, not the mail", `since` cursor) → `peek_message` → `read_message` ("the only call that marks mail handled") [27]. Blocking wait was **deliberately cancelled** (mission 0003 / ADR 0011) after tabulating client tool-call caps — OpenAI Agents SDK 5 s, Cursor ~60 s and loop detection on long-poll tools, Claude Desktop ~4 min, Claude Code 5-min idle abort; replaced by a client-side SSE waiter: "Blocking a process is free; blocking an agent turn is not" [54]. Wake notice = sender + subject + id, "never a message body as an instruction"; recipient-owned `[interrupt] wake_from` allowlist with `max_per_minute = 4`; Claude Code hooks (SessionStart/UserPromptSubmit `additionalContext`, Stop exit 2 once per message via a watermark) [27][54]. GPL-3.0, one author, 587 commits [26].

**agent-mail-cli** — https://github.com/JuanjoFuchs/agent-mail-cli (npm `@juanjofuchs/agent-mail`, PyPI `agent-mail-cli`). `describe` returns the JSON schema so an agent learns the mailbox "without MCP setup, a daemon, or separate documentation"; SQLite at `~/.agent-mail/mail.db`; `send --from a:b --to c:d --subject --body --ref <path>` (body capped at 2000 chars, "substance goes in a file the message points at"); `watch` blocks the _process_ (1 s SQLite poll) up to 55 min to stay inside a one-hour prompt-cache window; `read` ≠ `ack`; every result returns `reachable` plus a `next` list of literal commands "computed from the state that call just observed" [29][55]. MIT, one author, 0 stars [28].

**Claude Code native** — Subagents can `SendMessage` `main` and named siblings; nesting to depth 3 [32]. Agent teams (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) give a shared task list and a mailbox per agent at `~/.claude/teams/{team}/inboxes/{agent}.json`; but "in non-interactive mode with the `-p` flag… Claude doesn't spawn teammates", one team per session, no nesting, lead fixed [30]. Verdict: excellent _safety model_ to copy, but Claude-only and not routable across Taut's separate machines.

Cursor: subagents return to the parent only; no session messaging [45]. OpenCode: subagents via Task/@mention; `opencode serve` is an external HTTP push (`POST /session/:id/message`), not an agent tool [42][43].

## 4. Chat as the bus — design

**Principle (from agent-inbox and Orca):** the Taut HTTP API + event log is the only source of truth; the MCP server and the `taut` CLI are thin clients of it [27]. A message is durable the moment `message.created` is appended (`agent-model.md` §6); delivery/wake is best-effort attention, never a precondition [3][21].

**New data.** `departments (id, company_id, name, coordinator_user_id, channel_id)`; `agents.department_id`. Messages gain an optional `intent`: `task | ask | reply | done | handoff | status | chat`, and `task_id`. A **task** = a thread in the department channel whose root message has `intent=task` (created by the coordinator's `@bruno …`, or by `taut_handoff`). Task state lives on the root: `open → working → waiting(ask_id) → done|failed|cancelled`, mirrored as `agent.task.*` events already in §6.

**Per-task credentials.** At spawn, Taut mints `TAUT_TOKEN` bound to `(agent_id, task_id, department_id)` with a short TTL and injects `TAUT_URL`, `TAUT_TASK_ID`, `TAUT_THREAD_ID` into the runtime's MCP config (section 3). The server stamps `from` from the token — never a parameter [21] — and rejects lifecycle calls whose `task_id` does not match (Orca's dispatch-capability fencing, which stops a stale retry completing the current attempt) [3].

**Tool surface (MCP `taut`, mirrored 1:1 by the `taut` CLI, plus `taut describe` that prints the schema [29]):**

- `taut_roster()` → department members, runtime kind, presence (`idle|working|waiting`), unread count [21].
- `taut_send(to, text, refs?, intent?)` → posts in the current task thread with an @mention; body capped (~2 KB) and `refs` are file paths / message seqs, "coordination, not content" [29].
- `taut_inbox(since_seq?, wait_ms?, ack?)` → unread messages addressed to this agent, returned as a whole batch replayed until acked [2]; optional long-poll on the WebSocket (server holds ≤ 10 min).
- `taut_ask(to, question, options?, timeout_ms)` → creates a `message{intent:ask}` in the thread, sets task state `waiting`, and blocks (see below). Returns `{answer}` or `{pending, ask_id}` for `taut_ask --resume ask_id` [3].
- `taut_done(outcome: succeeded|failed, summary, files_changed?)` → exactly once per task; posts the summary, finalises the thread, fires the existing "agent task done" notification. Required `summary` mirrors Bernstein's `worker-completion/v1` [9].
- `taut_handoff(to, spec, refs)` → creates a _child_ task thread assigned to `to`, linked by `parent_task_id`; the child's `taut_done` posts back into the parent thread.

**Routing policy — enforced by the server, not the prompt:**

1. `agent → coordinator` is always allowed and is the default target when `to` is omitted (the coordinator is a thread participant, so §6 "reply in a thread I'm in" already notifies them).
2. `agent → agent` inside the same department is allowed, but the message always lands in a task thread of the department channel, so the coordinator sees every exchange without opting in. No agent DMs.
3. Cross-department: `taut_send`/`taut_handoff` to another department returns `403 needs_gate` and posts a _gate_ message (`intent:ask`, options `approve|deny`) to **both** coordinators. Only humans resolve gates — "the coordinator never auto-resolves gates" [7]. On approval the server creates the child task in the target department under that coordinator.

**What a task thread looks like.**

```
#backend · thread "Task tsk_91: migrate sessions table"
├─ @maria (coordinator)  intent=task   → assigned @bruno, state=open
├─ @bruno                streaming…    "Reading migrations/…"           (agent.task.delta)
├─ @bruno → @maria       intent=ask    "Drop `legacy_id` or keep nullable?" [drop|keep]  state=waiting
├─ @maria                intent=reply  "keep"                                              state=working
├─ @bruno → @ana         intent=handoff "Write the rollback script" → child tsk_92 (state chip)
├─ @ana                  intent=done   "Rollback script in db/rollback_091.sql"  (tsk_92 done)
└─ @bruno                intent=done   outcome=succeeded, summary, files_changed=[…]      state=done
```

Every line is an ordinary `message.created` event with `seq`, so a coordinator's reconnect replays it and a future "board" view is just `SELECT … WHERE intent='task'`.

**How an agent blocks on a reply.** Nobody who blocked the _agent turn_ kept it: postal-mcp's infinite `check_mail` was abandoned, agent-inbox cancelled its wait tool after measuring client caps (Cursor ~60 s with loop detection, Claude Code 5-min idle abort), and AgentsRoom refuses to ship one [25][27][21]. So `taut_ask` long-polls `GET /asks/:id?wait=<ms>` only briefly — default 45 s, per-runtime ceiling below the client's tool-call cap — and returns either `{answer}` or `{pending, ask_id}` [27]. On `pending` the preamble instructs the agent to end its turn with `taut_done(outcome: waiting)`; Taut **parks** the task (`state=waiting`, process exits, no tokens burn) and, when the reply lands, re-spawns the runtime with its session resumed and the answer as the prompt — `claude -p --resume <session_id>` [33], `codex exec resume <SESSION_ID>` [37], `opencode run --session <id>` [41], Cursor via a fresh prompt containing the thread transcript. The `taut` CLI additionally offers `taut inbox --wait` for shell scripts, which blocks the _process_ (agent-mail-cli's `watch`), not a model turn [29]. Inbound messages to a `working` agent are never injected into the PTY (the Orca failure class [6]) and never delivered while it is waiting on its human (AgentsRoom's "writing into that prompt would answer in your place" [21]); they are queued and returned on the next `taut_inbox` call, which the preamble tells the agent to make at checkpoints and immediately before `taut_done` [3]. On Claude Code a `UserPromptSubmit`/`SessionStart` hook may add a one-line notice (sender + subject + id, never the body) [27][33]. Inbound to an `idle` agent = a new task spawn with the message as prompt.

**Preventing loops and runaway chatter.**

- _Turn cap per task thread:_ a configurable budget (default 20) of agent-authored `send/ask/handoff` messages; the 21st returns `429 needs_coordinator` and posts a gate. Coordinators can raise it per task.
- _Handoff depth cap_ (default 2) — a child of a child cannot hand off again (Orca `nested_worker_depth_exceeded`; Claude Code depth 3) [2][32].
- _Per-pair rate limit and duplicate suppression_ on the server: N messages/min per `(from,to)`, identical bodies within a short window dropped and the sender told not to resend — copied from Claude Code's inbound throttles [31].
- _Broadcast header:_ a message to several recipients carries "also sent to …; do not relay" [21].
- _No agent-to-agent DMs, no cross-department without a human gate, sender stamped by server_ — the structural limits that make a loop visible in one thread and killable by one `pause`.
- _Existing knobs:_ token/time budgets per task and concurrency limits (deferred in `agent-model.md`) become the hard stop.

## 5. Recommendation

**Build natively.** None of the twelve tools is a fit as a dependency: the credible ones are desktop apps that own the terminal (Orca, AgentsRoom, Emdash, Composio AO, Conductor) or same-host SQLite files (agmsg, postal-mcp, Claude Squad), and Taut's agents are one-shot processes on separate machines talking to a server that already has a durable, ordered, replayable log. Chat-as-bus costs one MCP server (~6 tools), one CLI, one `departments` table, an `intent` column, and the routing/limit rules above — all of it on the existing `events` table and WebSocket. The PTY-injection route that Orca chose is precisely the one whose issue tracker warns against it [6].

**Depend on nothing** beyond the runtimes' own MCP loaders (section 3), which all four support headlessly today [33][36][38][41]. Do not build on Claude Code teams (interactive-only, Claude-only), cross-session messaging (cross-machine only through Anthropic's Remote Control), Codex `multi_agent`/`queue` (same host), or OpenCode `serve` (external push, no auth beyond basic) [30][31][44][43]. Keep watching Composio AO's "project orchestrator" — it validates the "coordinator is just another member with a CLI skill" shape, and its #4951 is the warning that worker events must be able to wake a coordinator turn [18].

**Borrow:** Orca — dispatch-scoped capability token, `task_id`+`dispatch_id` on every lifecycle call, `check --ack` batch replay, human-only gates, and the worker preamble ("never use AskUserQuestion; use ask; check inbox before done") [2][3][7]. AgentsRoom — persist-first, notice-not-body, `read/accepted/replied` as distinct facts, server-stamped sender, rate-limited sends, broadcast "do not relay" header, hold delivery while the recipient waits on its human [21]. agent-inbox — one API with MCP/CLI as clients, tiered reads with a cursor, onboarding prompt served by the hub, recipient-owned interrupt allowlist, and its client tool-call-cap table [27]. agent-mail-cli — `describe`, state-derived `next` commands, 2 KB body + `--ref`, process-level `watch` sized to the prompt-cache window [29]. Bernstein — closed message `kind` vocabulary and a completion contract instead of prose [9]. Composio AO — durable facts + derived status + CDC fan-out, and `blocked` vs `waiting_input` states that automation must never answer [18]. Claude Code — inbound throttles, duplicate drop, hold/accept/refuse per session [31].
